## 5. 数据模型

```sql
-- 源
sources(
  id INTEGER PK,
  name TEXT,
  url TEXT UNIQUE,          -- feed 地址
  module TEXT,              -- 'agent' | 'bigdata'
  enabled INTEGER DEFAULT 1,
  last_ok_at DATETIME,
  fail_count INTEGER DEFAULT 0,
  created_at DATETIME
)

-- 条目
items(
  id INTEGER PK,
  source_id INTEGER FK,
  module TEXT,
  title TEXT,
  url TEXT,
  url_hash TEXT UNIQUE,     -- 去重键
  published_at DATETIME,
  summary TEXT,             -- 源自带摘要或正文前 N 字
  fetched_at DATETIME,
  clicked_at DATETIME       -- 隐式反馈：我点开过
)

-- 打分
item_scores(
  item_id INTEGER PK FK,
  score REAL,               -- 0-100
  reason TEXT,              -- 一句「为什么值得看」
  model TEXT,
  prompt_version TEXT,
  scored_at DATETIME
)

-- 抓取日志
fetch_runs(
  id INTEGER PK,
  source_id INTEGER FK,
  started_at DATETIME,
  finished_at DATETIME,
  status TEXT,              -- ok | http_error | parse_error | timeout
  http_status INTEGER,
  items_new INTEGER,
  error TEXT
)
```

**去重规则（v1）**：`url_hash` 唯一约束。标题相似度去重留到 v2。

**铜币拍卖的表结构见 §14.5**：独立命名 `coin_*`，与上述四张表无外键关联。


## 6. 抓取管道

1. 读取 `enabled=1` 的源
2. 逐个抓取（串行 + 超时 10s，失败不阻塞其他源）
3. 解析条目 → 计算 `url_hash` → 已存在则跳过
4. 新条目入库（`items`，`module` 继承自源的配置）
5. 写 `fetch_runs` 日志；成功则更新源 `last_ok_at` 并清零 `fail_count`，失败则 `fail_count += 1`
6. 对**当日新增且未打分**的条目调用 LLM 打分
7. 生成当日日报视图

**失败处理**：单源失败只记录日志，不影响整体；源连续失败 ≥3 次在界面上标红。

**补拉**：**已取消**（2026-10-15，见 §9）：启动不再自动抓取；要补就跑「运行控制」页的「立即运行」。


## 7. LLM 打分

- **输入**：条目标题 + 摘要（截断控制 token）+ `module` + 该入口的关注点描述
- **输出**：严格 JSON

```json
{ "score": 82, "reason": "讲了多智能体任务拆分的三种失败模式，和你正在做的调度相关" }
```

- **打分口径**：与入口关注点的相关度、信息密度、时效性；理由必须具体到「这条讲了什么、为什么和你有关」，禁止「内容优质」这类空话（理由是我以后校准排序的唯一依据）
- **成本**：每条一次调用，入池量 × 单条 token，预期每天几毛到一两元
- **失败兜底**：单条打分失败不影响其他条目；`item_scores` 缺失的条目在日报中排在末尾
- **排序**：按 score 降序，取前 5-10 条进日报；未打分的排在最后


## 8. 页面

| 页面 | 内容 |
|---|---|
| 首页 / 日报 | 今日精选 5-10 条（标题、来源、打分、理由、链接）；点击链接时记录 `clicked_at` |
| 入口视图 | Agent / 大数据两个筛选视图，展示该入口的今日列表 |
| 历史搜索 | 关键词 + 时间范围 + 入口筛选，结果分页 |
| 源管理 | 源列表、启停开关、最近成功时间、失败次数（标红） |
| 运行控制 | 五个功能（知识抓取 / 打分、铜币采集 / 回采 / 查价）的启停 + 「立即运行」；开关存库、重启保留（§9） |
| 基金 | 占位页，仅显示「未启用」 |
| 铜币·专场列表 | 画像命中的专场卡片（拍卖时间、专场名称、店铺头像、4 张商品图、拍品数、围观次数）；无命中的专场不展示（§14.7） |
| 铜币·拍品页 | 单专场：店铺头（头像/名称/认证/拍卖时间/专场名/押金/拍品总数/推荐拍品数）+ 推荐拍品（名称/起拍价/当前价/推荐价/≤3 图）（§14.7） |
| 铜币·画像 | 结构化标签列表，可启停 / 改权重 / 增删（§14.2） |


## 10. 验收标准（v1 完成定义）

1. 配置里写上 3-5 个真实源，能抓到条目并入库
2. 新条目能被 LLM 打分，且理由具体、可反驳
3. 首页能看到当日 5-10 条精选，点击能跳转且被记录
4. 历史搜索能按关键词搜到过去抓的条目
5. 某个源挂掉时，页面能标红提示，且不影响其他源
6. **连续多天我主动打开它**

> 铜币拍卖的验收标准见 **§14.12**（本模块独立验收，不与上述 6 条混算）。

## 12. 风险与对策

| 风险 | 对策 |
|---|---|
| 内容不够好 → 不再打开（首要风险） | **先做内容质量，最后做外壳**；开发顺序见 §13 |
| 源失效 | 记录 `last_ok_at` / `fail_count`，界面标红；单源失败不阻塞整体 |
| 本机常驻不可靠 | 接受漏天，不再启动补拉；需要时在「运行控制」页手动补跑（§9） |
| 排序逻辑无人校准 | 隐式点击记录 + 理由文本；后续用点击分布调整 prompt |
| 已有替代方案够用 | 若跑通后仍不如直接刷 RSS，应果断停做，不要沉没成本 |

> 铜币拍卖模块另有独立风险清单，见 **§14.9**。


## 13. 开发顺序（重要）

里程碑清单里包含「外壳入口」，但**顺序必须反过来**：

1. **先蹚管道**：SQLite 建表 + 抓 3-5 个真实源 + 入库
2. **再上打分**：接 LLM，产出打分与理由，验证理由是否可反驳
3. **再做日报首页**：能看到 5-10 条精选，并能点击
4. **补历史搜索**
5. **最后做外壳**：两个入口视图、导航、基金占位页

顺序搞反会得到一个漂亮的空壳。

> **铜币拍卖是独立的一条开发线**（2026-10-09 增补），顺序见 §14.10：**先画像 → 再打通采集 → 再匹配定价 → 最后两个页面**。它不参与上面这条知识聚合的顺序约束，但也遵守同一条原则——先蹚通最不确定的一环（这里是采集接口），再谈页面。
