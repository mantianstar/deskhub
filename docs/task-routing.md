# 任务类型与执行路径

> 从 [RULES.md](../RULES.md) §零 分出的专题细则：判定顺序、五类路径、子代理输入模板、历史校准。
> 开工第一件事是**定类型**，再决定要不要任务卡、走不走子代理；类型判错比路径走歪更贵。

## 一、判定顺序（自上而下，命中即停）

1. **会改仓库吗？** 不会，只是问「是什么 / 为什么 / 在哪」→ **Q**。
2. **是「有现象、要根因」吗？**（数据不对、匹配错、该显示的没显示）→ **D**。
3. **要改页面长什么样 / 怎么交互 / 字段怎么排吗？** 形态没定稿 → **P**。
4. **跨 ≥3 个文件、跨「路由 + 模板 + 数据 + 测试」，或需求里有 ≥2 个说不清的取舍？** → **L**。
5. 其余（一句话能复述、改一条链路、≤2 个文件）→ **S**。

专用：只想看 token 花在哪 → 调 `token-analyst`，按 Q 处理（只读）。
判定结果写在任务卡首行（`类型：S`）；Q / D 不写卡，但回复里点明类型。

## 二、五类路径

| 类型 | 任务卡 | 子代理 | 轮数上限 | 产出 |
|---|---|---|---|---|
| Q 问答 / 解释 | 不写 | 无（token 复盘除外） | ≤3 | 回答；不写文件 |
| D 排查 | 不写（只读） | `bug-reproducer`（跨 ≥2 文件或口径 / 数据类） | ≤8 | 现象 → 根因（文件:行）→ 复现 → 修不修由人定 |
| S 小改 | 写（标 S） | 无 | ≤10 | 按五轮模板交付 |
| P 页面 | 写（标 P） | `page-prototyper` → 主对话落地 | ≤12 | 原型 + 类名清单 + CSS 范围 → 代码 |
| L 大任务 | 写（标 L） | `planner`（口径不清必走）；执行片可 `general_purpose_task` | 单任务 ≤15 / 阶段 ≤80 | 需求卡 → 分片交付 → 全量验证 + CHANGELOG |

### Q · 问答 / 解释

- 不改任何文件、不写 CHANGELOG；读取只为回答服务，≤3 个文件、≤3 轮。
- 答的过程发现「这其实要改」→ 停，按 S / L 重新出卡，不在 Q 里顺手改。

### D · 排查

- 只读。产出固定四段：现象 / 根因（文件 + 行号）/ 复现（命令或用例）/ 修复建议（不实施）。
- **调 `bug-reproducer`**：现象要跨 ≥2 个模块追（例：品相台账有、画像没标），或涉及口径 / 数据源。单文件一眼能看出的不调。
- 要修 → 另开 S 卡（改动链 = 根因那一段），不把「查 + 修」塞进一个任务。

### S · 日常小改

- 走 [PROJECT_MAP.md](../PROJECT_MAP.md)「速查：S · 日常小改」五轮模板，任务卡首行标 `类型：S`。
- 第 2 轮收集完若命中 ≥3 个文件或跨层 → 停手上报，升 L，不硬按 S 做完。

### P · 页面

- 先调 `page-prototyper`：输入「页面路径 + 要改的区域 + 字段 / 交互清单」，拿回可原样落地的 HTML + 类名清单 + CSS 迁移范围。
- 原型给的「落地可能走形的点」→ 与用户确认后再落地；落地按 S 五轮执行，不重新设计。
- 纯后端、数据口径、采集解析类需求不进 P。

### L · 大任务 / 里程碑

1. **planner**：输入 = 需求原句 + 硬约束 + 只读范围；输出五段需求卡（验收句 / 待确认 / 改动链 / 取舍 / 明确不做）。
2. **确认**：「待确认」逐条交给用户拍板（`AskUserQuestion`），拍完再动手；主对话不替用户选。
3. **分片**：按改动链切片，每片 ≤3 个文件、能独立验证；优先进主对话做，片间无依赖且量大时才用 `general_purpose_task`。
4. **收口**：每片跑相关测试；全片完成后跑全量 + CHANGELOG 一条。

口径已经写清（有字段、有验收句）但只是文件多 → 可直接执行，不必先 planner；类型仍是 L。

## 三、类型升降级

- Q 发现要改 → 转 S / L，重新出卡。
- D 定位完要修 → 新开 S 卡，不续在原任务里改。
- S 第 2 轮发现跨 ≥3 文件 / 跨层 → 停手升 L，补任务卡。
- P 原型暴露后端缺数据源 → 原型结论保留，另开 S / L 卡补数据。
- L 分片后某片退化为一句话改动 → 该片按 S 五轮做，类型仍记 L（片号不变）。

## 四、子代理调用

**输入四要素**（缺一条就别调）：

1. 背景：一句话说清模块与现状。
2. 需求原句 / 现象：用户原话，不改写。
3. 验收句：操作 → 可判定结果。
4. 边界：只读范围、禁改文件、轮数、输出行数。

**回执**：子代理返回必须带自报三行（轮数 / 搜索与读取 / 写入与命令），主对话原样并进「子代理层」回执；没自报写「未自报」。
**记录**：调用过子代理的轮次追加 `data/conversations/{YYYY-MM-DD}.md`（见 [conversation-log.md](./conversation-log.md)）。

| 场景 | 子代理 | 不该用的场景 |
|---|---|---|
| 需求要变成可验收方案 / 口径不清 | `planner` | 单文件单函数的小改、纯问答 |
| 现象要追到根因 | `bug-reproducer` | 已知道根因、只差改代码 |
| 页面 / 交互形态未定 | `page-prototyper` | 纯后端、数据口径、采集解析 |
| token 消耗要复盘 | `token-analyst` | 与成本无关的功能改动 |
| 已规划好、可独立完成的实现片 | `general_purpose_task` | 需要逐步和用户确认的探索 |
